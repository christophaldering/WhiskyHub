## Entscheidung 1: Wishlist-Match-Strategie → Variante (ε), mit kleiner Korrektur

Variante (ε) ist richtig, weil die Wishlist semantisch ein Notizzettel ist.
"Lagavulin 16" auf der Liste = Absicht, nicht Sub-Cask-Genauigkeit. False-
Positives sind hier feature-passend, nicht Bug.

ABER: Deine Code-Skizze hat eine zu großzügige Stelle:

```typescript
((e.distillery || "").toLowerCase().trim() === nDist || !e.distillery)
```

Das matcht einen Wishlist-Eintrag OHNE Distillery auf JEDEN Whisky. Wenn
jemand nur "Cask Strength Bourbon" notiert hat, sollte das nicht für einen
Lagavulin matchen.

Korrigierte Match-Logik:

```typescript
const wl = await storage.getWishlistEntries(participantId);
const nName = (whisky.name || "").toLowerCase().trim();
const nDist = (whisky.distillery || "").toLowerCase().trim();

const matchedWishlist = wl.find(e => {
  const eName = (e.name || "").toLowerCase().trim();
  const eDist = (e.distillery || "").toLowerCase().trim();
  
  // Name MUSS matchen
  if (eName !== nName) return false;
  
  // Distillery: wenn beide gesetzt, müssen sie matchen
  // Wenn Wishlist-Eintrag KEINE Distillery hat, reicht Name-Match
  // (User hat es absichtlich offen gelassen)
  if (eDist && nDist) return eDist === nDist;
  
  // Mindestens eine Seite hat keine Distillery → Name-Match reicht
  return true;
});

const inWishlist = !!matchedWishlist;
```

## Entscheidung 2: wishlistPriority mitliefern → JA

Praktisch kostenlos im selben Find-Call, hoher UI-Wert. Im Glance-Use-Case
(User steht vor Flasche) ist Priorität die entscheidende Handlungs-
information: "Hohe Priorität, kaufen!" vs "Niedrige Priorität, war eh nur
Pflichtnotiz".

Im Personal-Layer ergänzen:

```typescript
wishlistPriority: matchedWishlist?.priority ?? null  // "low" | "medium" | "high" | null
```

`null` wenn nicht auf Wishlist. Default-Schema-Wert "medium" sorgt dafür,
dass bei Match fast immer ein Wert da ist.
