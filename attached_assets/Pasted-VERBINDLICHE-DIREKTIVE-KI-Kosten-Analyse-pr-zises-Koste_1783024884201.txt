ZIEL:
Teil A (rein lesend): Aus ai_usage_log die reale Nutzungsverteilung der
letzten 90 Tage auswerten und mit Kostenschätzungen pro Aufruf zu einer
ersten "Kosten pro aktivem Nutzer/Monat"-Zahl verdichten — die
Entscheidungsgrundlage fürs Preismodell.
Teil B (kleine additive Erweiterung): ai_usage_log um model, tokensIn,
tokensOut, durationMs erweitern und an den Schreibstellen befüllen,
damit künftige Auswertungen echte statt geschätzter Kosten zeigen.

═══ TEIL A — AUSWERTUNG (nur SELECT, keinerlei Schreibzugriff) ═══

SCHRITT A0 — DIAGNOSE:
1. Zeige alle distinct featureId-Werte in ai_usage_log + Zeilenzahl je
   Feature (letzte 90 Tage).
2. Zeige, welche Schreibstellen in server/routes.ts ai_usage_log
   befüllen (Suche "aiUsageLog") — Liste featureId → verwendetes Modell
   (gpt-5, gpt-5-mini, realtime, transcribe, dall-e) aus dem umgebenden
   Code ableiten. Falls ein KI-Aufruf im Code KEINEN Log-Eintrag
   schreibt (Lücken!), diese Aufrufe explizit auflisten — sie fehlen
   sonst in jeder Kostenrechnung.

SCHRITT A1 — AUSWERTUNGS-QUERIES (read-only, Ergebnisse als Tabellen):
1. Nutzung je Feature je Monat (letzte 3 Monate): featureId, Monat,
   Aufrufe, distinct Nutzer.
2. Nutzung je Nutzer (anonymisiert als P1, P2, ...): Aufrufe gesamt,
   Aufrufe je Feature-Gruppe (voice / text-cooper / reports / bilder /
   sonstiges), aktive Tage.
3. Verteilung: Median und p90 der Aufrufe pro aktivem Nutzer/Monat
   (der p90-Nutzer bestimmt das Fair-Use-Limit, nicht der Median).

SCHRITT A2 — KOSTEN-HOCHRECHNUNG:
Je Feature-Gruppe eine Kostenannahme pro Aufruf ansetzen und BEGRÜNDEN
(Modell + typische Tokenzahl/Dauer aus dem Code ableiten, z.B.
max_completion_tokens-Werte; Realtime über typische Session-Dauer —
falls unbekannt, Spanne 5/10/20 Min als Szenarien). Daraus:
- Kosten pro aktivem Nutzer/Monat: Median-Szenario und p90-Szenario
- Anteil der Voice-Kosten an den Gesamtkosten
- Die eine Kennzahl fürs Pricing: "Premium-Preis ≥ 3× erwartete
  Ø-Kosten" — erfüllt bei 69 €/Jahr ja/nein, und bei welchem
  Voice-Kontingent kippt es?
ALLE Annahmen explizit als Tabelle ausweisen (Modell, Preis je 1M
Tokens bzw. je Minute, angenommene Menge) — Christoph muss jede
Annahme nachvollziehen und korrigieren können. KEINE Scheingenauigkeit:
Spannen statt Punktwerte, wo Daten fehlen.

═══ TEIL B — PRÄZISES LOGGING (additiv, nach A) ═══

SCHRITT B1 — PLAN (bestätigen):
1. Schema: ai_usage_log + vier nullable Spalten:
   model varchar("model"), tokensIn integer("tokens_in"),
   tokensOut integer("tokens_out"), durationMs integer("duration_ms").
   ADDITIV, kein Default-Backfill, bestehende Zeilen bleiben null.
   → drizzle-kit push macht Christoph manuell.
2. Schreibstellen: An jeder in A0.2 gefundenen Stelle die neuen Felder
   befüllen — model aus der Aufruf-Konstante; tokensIn/Out aus
   response.usage (Chat Completions liefern das); durationMs für
   Voice-Sessions aus der Session-Dauer (falls im finalize verfügbar,
   sonst null lassen und als offen melden).
3. In A0.2 gefundene LÜCKEN (KI-Aufrufe ohne Logging) schließen:
   Log-Eintrag mit allen Feldern ergänzen — fire-and-forget, darf
   den Nutzerpfad nie blockieren oder bei Fehler brechen.
