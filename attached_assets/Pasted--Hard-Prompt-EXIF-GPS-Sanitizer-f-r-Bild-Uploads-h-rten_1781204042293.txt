# Hard Prompt: EXIF/GPS-Sanitizer für Bild-Uploads härten

**Datum:** 11.06.2026 · **Priorität:** HOCH (Sicherheit, Dirk-Feedback 20.05.2026)
**Betroffene Datei:** ausschließlich `server/routes.ts` (+ `package.json` für eine neue Dependency)

---

## Kontext & Ziel

Nutzer-Fotos (Flaschen, Events, Profile) können GPS-/Standortdaten in den EXIF-Metadaten enthalten. Kombination „wertvolle Sammlung + Standort" ist ein reales Sicherheitsrisiko. Alle Bild-Uploads laufen durch den Chokepoint `uploadBufferToObjectStorage()` → `maybeCompressImage()` in `server/routes.ts`. Das dortige sharp-Re-Encoding strippt EXIF bereits implizit — **aber mit zwei Lücken, die geschlossen werden müssen:**

1. **Fail-open:** Schlägt sharp fehl (Catch-Block), wird das Original **mit allen Metadaten** hochgeladen. Kritisch, weil vorgebaute sharp-Binaries HEIC/HEVC (iPhone-Standardformat) oft nicht dekodieren können — genau iPhone-Fotos würden dann roh durchrutschen.
2. **Content-Type-Lücke:** Bilder mit `application/octet-stream`, leerem oder falschem Content-Type umgehen den Filter komplett (Passthrough mit Metadaten).

**Ziel:** Kein Bild verlässt den Upload-Pfad mit EXIF-Metadaten. Fail-closed statt fail-open. Nicht-Bilder (PDF, Audio) bleiben unberührt.

## Plan (nach Bestätigung umsetzen)

### 1. Magic-Byte-Sniffing ergänzen

Neue Hilfsfunktion direkt über `maybeCompressImage`:

```typescript
// Erkennt Bildformate an Magic Bytes — unabhängig vom (oft falschen) Content-Type.
function sniffImageType(buffer: Buffer): string | null {
  if (buffer.length < 12) return null;
  if (buffer[0] === 0xff && buffer[1] === 0xd8 && buffer[2] === 0xff) return "image/jpeg";
  if (buffer[0] === 0x89 && buffer[1] === 0x50 && buffer[2] === 0x4e && buffer[3] === 0x47) return "image/png";
  if (buffer.toString("ascii", 0, 4) === "RIFF" && buffer.toString("ascii", 8, 12) === "WEBP") return "image/webp";
  const ftypBrand = buffer.toString("ascii", 8, 12);
  if (buffer.toString("ascii", 4, 8) === "ftyp" && ["heic", "heix", "hevc", "heif", "mif1", "msf1"].includes(ftypBrand)) return "image/heic";
  if ((buffer[0] === 0x49 && buffer[1] === 0x49 && buffer[2] === 0x2a) || (buffer[0] === 0x4d && buffer[1] === 0x4d && buffer[2] === 0x2a)) return "image/tiff";
  return null;
}
```

In `maybeCompressImage` ganz am Anfang: Wenn der deklarierte Content-Type NICHT im `COMPRESSIBLE_IMAGE_TYPES`-Set ist, per `sniffImageType()` nachprüfen. Trifft das Sniffing ein Bildformat, mit dem gesnifften Typ weiterverarbeiten (statt Passthrough).

### 2. HEIC-Fallback-Decoder

Falls Schritt-0-Test ergab, dass sharp HEIC nicht dekodiert:

```bash
npm install heic-convert
```

In `maybeCompressImage`: Wenn der (deklarierte oder gesniffte) Typ `image/heic`/`image/heif` ist, **zuerst** `heic-convert` (Output: JPEG, quality 0.9) anwenden, dann den JPEG-Buffer wie gewohnt durch die bestehende sharp-Pipeline (`rotate → resize → webp`) schicken. `heic-convert` ist pure JS/WASM (libheif + libde265), keine nativen Build-Schritte.

Import als dynamischer Import im Funktionskörper (wie sharp dort bereits gehandhabt wird), damit der Server-Start nicht belastet wird.

### 3. Fail-closed für Bilder

Den Catch-Block in `maybeCompressImage` ändern: Wenn der Input als Bild deklariert ODER gesnifft wurde und die Sanitierung fehlschlägt, **Error werfen** statt Original zurückgeben:

```typescript
throw new Error(`Bild-Sanitierung fehlgeschlagen (${effectiveType}): ${err instanceof Error ? err.message : err}`);
```

Nicht-Bilder (PDF, Audio, alles ohne Bild-Magic-Bytes) verhalten sich wie bisher: unveränderter Passthrough.

**Begründung fail-closed:** Ein Bild, das weder sharp noch heic-convert lesen kann, ist mit hoher Wahrscheinlichkeit korrupt oder kein Bild — es zu speichern hat keinen Produktwert, aber das Metadaten-Risiko bliebe bestehen.

### 4. Logging

Eine Zeile pro sanitiertem Upload: `console.log("[image-sanitize]", effectiveType, "→ webp,", originalBytes, "→", outBytes)`. Beim Fail-closed-Throw: `console.error("[image-sanitize] REJECTED", ...)`.
