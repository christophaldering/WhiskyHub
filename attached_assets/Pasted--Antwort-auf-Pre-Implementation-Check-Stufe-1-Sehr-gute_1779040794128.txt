## Befund nach Rückprüfung

Beide Tabellen führen das Feld `whiskybaseId` (Whiskybase-Katalognummer):
- `whiskies.whiskybaseId` (text, nullable) — shared/schema.ts L201
- `whiskybase_collection.whiskybaseId` (text, notNull) — shared/schema.ts L639

Die kanonische Brücke ist im Code bereits etabliert:
- `server/storage.ts L162`: `buildCommunityWhiskyKey()` bevorzugt
  `wb:${whiskybaseId}` als Primary Key, fällt auf name+distillery zurück
- `server/storage.ts L439, L1736`: `findWhiskiesByWhiskybaseIdForHost()`
  ist exakt der Lookup-Pattern, den wir hier auch brauchen

Damit ist Variante (α) Name-Match unterlegen — sie ist nur der Fallback,
nicht die Primary Strategy.

## Entscheidung: Variante (δ) — whiskybaseId-Primary mit Name-Fallback

Implementiere `inCollection` so:

```typescript
const collectionItems = await storage.getWhiskybaseCollection(participantId);

// Primary: match by whiskybaseId (robust, no false positives)
let matchedItem: WhiskybaseCollectionItem | undefined;
if (whisky.whiskybaseId) {
  matchedItem = collectionItems.find(it => it.whiskybaseId === whisky.whiskybaseId);
}

// Fallback: name + distillery match (only if no whiskybaseId on whisky)
if (!matchedItem && !whisky.whiskybaseId) {
  const normName = (whisky.name || "").toLowerCase().trim();
  const normDist = (whisky.distillery || "").toLowerCase().trim();
  matchedItem = collectionItems.find(it =>
    (it.name || "").toLowerCase().trim() === normName &&
    (it.distillery || "").toLowerCase().trim() === normDist
  );
}

const inCollection = !!matchedItem;
const collectionSince = matchedItem?.addedAt ?? matchedItem?.createdAt?.toISOString() ?? null;
```

Wichtig: Fallback NUR wenn `whisky.whiskybaseId` null/leer ist.
Wenn whisky.whiskybaseId existiert UND kein Match: ehrlich `false`,
NICHT auf Name-Fallback ausweichen (würde false-positive geben).

## collectionSince — Datums-Handling

`addedAt` ist text (z.B. ISO-String aus Whiskybase-Import), `createdAt`
ist timestamp. Liefere `addedAt` bevorzugt als String, sonst
`createdAt.toISOString()` als String. Frontend bekommt einheitlich String
(oder null). Kein Datums-Parsing im Backend.

## Konsequenzen für die Spec

- Collection-Check ist Teil von Stufe 1 (nicht deferred)
- Keine neue Storage-Methode, keine Schema-Änderung
- Performance: O(n) über User-Collection (typisch < 200 Items) ist
  vertretbar in Stufe 1; bei Bedarf später durch direkten DB-Query
  ersetzen
