SCHRITT 1 — PLAN (zur Bestätigung vorlegen, NICHT ausführen ohne OK):

A) Server: Neues Tool update_identity im converse-Endpoint

   Tool-Definition analog update_ledger, aber mit Identity-Feldern:
   {
     name?: string,
     distillery?: string,
     region?: string,
     country?: string,
     abv?: number,
     price?: number,
     currency?: string,
     wb_number?: string,
     vintage?: string,
     age_statement?: string
   }

   Tool-Call-Handling:
   - mergeIdentityLedger: neue Werte überschreiben ältere (last-mention-wins),
     undefined-Felder bleiben unverändert
   - _sourceVoice: true als unveränderlicher Marker auf dem gesamten Objekt
   - identityLedger wird analog zum sensorischen Ledger über den Request-Body
     hin- und hergereicht (kein Server-seitiger Session-State nötig, sofern
     die Diagnose das bestätigt)

   System-Instruction-Ergänzung (MINIMAL):
   - Einzige Ergänzung: Cooper soll update_identity aufrufen, wenn der
     Tastende von sich aus identifizierende Angaben zur Flasche macht.
   - KEINE Änderung am sokratischen Gesprächsstil, KEINE neue Aufforderung
     an Cooper, aktiv nachzufragen. Ergänzung darf die Persona-Instruction
     nicht verwässern.
   - Cooper erwähnt das Tool-Calling dem Taster gegenüber nie.

   finalize: true Erweiterung:
   - identityLedger (wenn nicht leer) ans ImpressionResult anhängen
   - Nur tatsächlich befüllte Felder zurückgeben, keine leeren Strings
     oder null-Werte

B) Typen: ImpressionResult erweitern (client/src/lib/impressionApi.ts)

   IdentityLedger-Typ (alle Felder optional):
   {
     name?: string
     distillery?: string
     region?: string
     country?: string
     abv?: number
     price?: number
     currency?: string
     wb_number?: string
     vintage?: string
     age_statement?: string
     _sourceVoice: true
   }

   ImpressionResult bekommt: identityLedger?: IdentityLedger
   ConverseResult bekommt: identityLedger?: IdentityLedger (für
   Turn-zu-Turn-Weitergabe analog Ledger)

   EMPTY_IDENTITY_LEDGER exportieren (analog EMPTY_LEDGER).

C) Client: ImpressionCapture.tsx — identityLedger durchreichen

   - identityLedger-State parallel zum sensorischen Ledger halten
   - Bei jedem converseImpression-Call: aktuelles identityLedger mitsenden,
     zurückgegebenes identityLedger in State mergen
   - Bei finalizeImpression: identityLedger mitsenden, zurückgegebenes
     identityLedger an onApply(ImpressionResult) weitergeben
   - KEINE UI-Änderung in ImpressionCapture selbst — der Tastende sieht
     nichts vom identityLedger während des Gesprächs

D) Client: LabsSolo.tsx — Formular-Vorausfüllung

   handleImpressionApply erhält identityLedger aus ImpressionResult.
   Wenn identityLedger befüllt:
   - Felder als Vorschläge in das Whisky-Anlage-/Zuordnungs-Formular
     schreiben (genauer Ziel-Komponente laut Diagnose bestimmen)
   - Konfliktlogik mit Check-Feature:
     → Wenn ein Feld bereits via Foto-Erkennung (_sourceVoice fehlt)
       befüllt ist UND der Wert abweicht: beide Varianten als auswählbare
       Chips/Buttons im Formular nebeneinander anzeigen, Nutzer tippt
       auf eine davon
     → Wenn beide Quellen übereinstimmen: Feld direkt vorausgefüllt,
       kein Konflikt-UI
     → Wenn nur eine Quelle vorhanden: direkt vorausgefüllt

E) LabsLive: KEIN identityLedger aktivieren

   Sicherstellen, dass der converse-Endpoint für LabsLive-Calls das
