SCHRITT 1 — PLAN (bestätigen):

A) Schema (shared/schema.ts, ADDITIV):
   1. Neue Tabelle consent_records:
      id (varchar, uuid default), participantId (varchar, notNull),
      consentType (varchar, notNull)  // 'research' | 'aggregate'
      textVersion (varchar, notNull), // z.B. 'v1-2026-07'
      granted (boolean, notNull),     // true=erteilt, false=widerrufen
      createdAt (timestamp, defaultNow)
      Index auf (participantId, consentType).
      APPEND-ONLY: Änderungen erzeugen neue Zeile, nie UPDATE/DELETE —
      der Verlauf ist der Audit-Trail.
   2. participants: zwei neue Spalten (Schnellzugriff, Wahrheit bleibt
      consent_records):
      researchConsent: boolean("research_consent").default(false)
      aggregateConsent: boolean("aggregate_consent").default(false)
   3. vocabulary_adoption: neue Spalte
      modelLabel: varchar("model_label")  // nullable; z.B. 'gpt-5-mini'
   → Nach Push: Christoph führt npx drizzle-kit push --force manuell aus.

B) Server:
   1. Konstante CONSENT_TEXT_VERSION = "v1-2026-07" (eine Stelle).
   2. POST /api/consent (auth via x-participant-id wie üblich):
      Body { consentType: 'research'|'aggregate', granted: boolean }.
      Schreibt consent_records-Zeile MIT textVersion + aktualisiert das
      Participant-Flag. Whitelist-validiert, 403 ohne gültigen Participant.
   3. GET /api/consent: aktueller Stand beider Flags + textVersion der
      letzten Erteilung (für Settings-Anzeige).
   4. PATCH /api/participants/:id: researchConsent/aggregateConsent NICHT
      direkt patchbar machen — Änderungen NUR über POST /api/consent
      (sonst umgeht man den Audit-Trail).
   5. vocabulary_adoption-Schreibstellen: modelLabel mit dem tatsächlich
      genutzten Modell befüllen (aus der jeweiligen Aufruf-Konstante,
      nicht hardcodiert doppelt).

C) Client — Settings (LabsTasteSettings.tsx):
   Neue Untersektion "Forschung & Daten" unter der bestehenden Privacy-
   Sektion, zwei Toggles analog shareStatsForBenchmarks, aber via
